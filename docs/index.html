Duplicates

Applied once

A repeated event id changes nothing. Pub/Sub delivers at least once, so this matters.

Bad messages

Dead-lettered

A malformed message goes to a separate topic instead of retrying forever.

Privacy

No raw user ids

A keyed hash is the only user identifier in Redis and in the logs.

One event, one recommendation

The API only accepts and answers. The worker does the writing. Redis holds the features.

Built to be operated

Probes that mean something

Liveness does not depend on Redis. Readiness does, so a bad Redis takes the pod out of rotation without a restart loop.

Searchable logs

One JSON line per action. Saved Splunk searches for latency, cold-start rate, dead letters and retries are in splunk/.

Safe rollouts

Zero unavailable during a rolling update, a deadline, a disruption budget, and a Jenkinsfile that undoes a failed rollout.

GCP shape

Terraform for Pub/Sub with dead letter, Memorystore, Cloud Run and separate publisher and subscriber service accounts.

What this does not prove

So you do not have to guess.

Not on GCP

Pub/Sub and Redis run as local stand-ins. The GCP Terraform is validated and scanned, never applied.

Synthetic data

The recommender is item-item co-occurrence. The offline lift will not carry over to real traffic.

Other CI systems

The Jenkinsfile and CircleCI config use the same steps as GitHub Actions and have not run on those systems.
